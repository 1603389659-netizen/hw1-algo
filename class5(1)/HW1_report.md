## 一、算法思想复述（自己的话，各 ≤ 5 行）

### 1.1 合并排序（merge_sort）——分治
1. **分解**：把长度 n 的数组从中间一刀切成两半，递归地分别排序左半和右半；子表长度 ≤ 1 时天然有序，作为递归终点。
2. **解决**：两半各自递归排序好后，交给合并函数。
3. **合并**：用双指针同时扫两个有序子表，每次取较小者放进结果；任一子表耗尽后把剩余部分直接拼上。
4. 时间复杂度 **O(n log n)**，稳定排序，原地性否（需 O(n) 额外空间）。

### 1.2 二分查找（binary_search）——也是分治
1. **前提**：查找表必须**有序**，否则折半判断毫无依据。
2. **分解**：取中点 `mid`，拿 `rates[mid]` 跟 target 比较，一次排除一半候选。
3. **解决**：若相等则命中；若 target 小则在左半继续；若 target 大则在右半继续。循环直到 `low > high` 时返回不存在。
4. 时间复杂度 **O(log n)**，前提破坏时结果完全不可预测。

### 2.2 增长规律解读

- **冒泡平均翻倍倍率 ≈ 4.21×**，与理论 O(n²) 给出的 2² = 4.00 高度吻合。
  二次方的本质就是：输入翻倍，工作量翻 **4 倍**。实测 4.07 / 3.93 / 4.64 三档均值 4.21，波动来自 Python 动态类型的常数项差异和 OS 调度噪声，但整体趋势非常清晰。

- **合并平均翻倍倍率 ≈ 2.10×**，与理论 O(n log n) 给出的约 2.00（略多一点）高度吻合。
  线性对数的本质：输入翻倍，n 翻倍是 ×2，log₂n 只多 1，相乘起来就是 ×2 略多一点。实测 1.97 / 2.20 / 2.14 均值 2.10，完美落在预期带内。

- **n=8000 时合并比冒泡快 182 倍**，远超"一个数量级以上"的检查点。而且差距仍在发散：从 n=1000 的 23× → n=8000 的 182×，这正好对应 n² 与 n log n 的渐近差。

### 2.3 关键实验设计细节
- 两种算法用**同一份随机数组**（固定 seed=42），输入不撒谎；
- 每次计时都传 `arr[:]` 副本，防止原地排序污染第二遍；
- 计时前先跑正确性断言，排对 `[8,3,5,1,9,2]` 才开始计时。

## 三、二分查找"未排序翻车"实验记录

### 3.1 实验目的
二分查找教科书上常说"前提是有序"，但很少演示"前提被破坏会怎样"。本实验故意在未排序数组上调用二分查找，直观感受"前提"二字的分量。

### 3.2 用例
- 故意构造极端坏数组：`[99, 7, 1, 12, 3, 20, 5, 8, 0]`（最大值 99 放最前，最小值 0 放最后）
- 在其上调用 `binary_search`，与线性扫描结果对比

### 3.3 观察到的现象

| 目标 | 二分返回 | 线性扫描返回 | 对比 |
|---|---|---|---|
| 5 | idx=6，比较 2 次 | idx=6 | 碰巧命中 mid——**巧合≠正确** |
| 0 | **idx=-1 ❌**，比较 3 次 | **idx=8** | 明明存在却"找不到" |

### 3.4 为什么会翻车（走一遍折半路径）

```
初始 low=0, high=8, target=0
mid=4 → arr[4]=3  > 0 → high=3   ← 被误导，以为 0 在左半
mid=1 → arr[1]=7  > 0 → high=0   ← 继续被误导
mid=0 → arr[0]=99 > 0 → high=-1  ← 走到头了，返回 -1
```

因为数组无序，`arr[mid]` 的大小**完全不能指示** target 应该在左还是右——折半逻辑的核心依据被架空，算法像无头苍蝇跳几步后就放弃了。**注意：这种失败没有任何报错或 warning**，就是默默返回 -1 或错误下标。这就是"前提被破坏"最阴险的地方。

### 3.5 学到的
- 前提条件要**写进文档、读入代码注释、最好能 assert**；
- 二分查找返回 -1 时，你根本不知道是"真没找到"还是"输入没排序"；
- 不要相信网上"随便传个 list 给二分查找"的示例——那是教学玩具，不是工程代码。

## 四、结论：什么规模该换什么算法

综合本次实测给出的实证结论：

| 规模 n | 推荐算法 | 理由 |
|---|---|---|
| **n < ~50** | 冒泡 / 插入 都能接受 | O(n²) 常数项很小，简单易写；Python 里 list.index 就是 O(n)，二分在此规模下甚至还没优势 |
| **50 ≤ n ≤ 几千** | 合并排序 / 归并排序 | O(n log n) 的优势开始显露；实测 n=1000 时冒泡就已经比合并慢 20+ 倍 |
| **n ≥ 8000** | 合并 / 快排 / Timsort（Python 内置 sorted） | 实测 n=8000 冒泡要 2.8 秒，合并只要 15 毫秒，差 182 倍——此时 O(n²) 已经**不可用** |
| **有序且大 n** | 二分查找 | O(log n)：100 万元素只需比较 ~20 次。但**必须先排序**，排序成本 O(n log n) 要算进总成本 |

一句话总结：**在不确定规模时，优先选 O(n log n) 的算法；只有在 n 很小、或输入几乎有序、或代码可维护性压倒一切时，才考虑 O(n²)。算法复杂度是少数能跨机器、跨语言、跨时代成立的"软物理定律"。**

### 5.1 给 merge_sort 加递归深度打印（15 分）

**实测结果**

| n | 实测最大深度 | 理论 ceil(log₂n) | 是否吻合 |
|---|---|---|---|
| 1000 | **10** | 10 | ✅ |
| 2000 | **11** | 11 | ✅ |
| 4000 | **12** | 12 | ✅ |
| 8000 | **13** | 13 | ✅ |

**为什么 log₂8000 ≈ 12.97，深度却是 13？** 因为每次递归都是 `mid = len//2`，长度为 8000 的数组需要切 12 次才剩长度 2 的子表，再切一次才到长度 1——正好 13 层。ceil(log₂n) 就是这个向上取整的结果。Python 默认递归上限是 1000，13 层远远碰不上。

### 5.2 benchmark 扩展：Python 内置 sorted 对比（15 分）

**三种排序横比（随机数组，同一份输入）**

| n | 冒泡 (s) | 自造合并 (s) | sorted (s) | 合并/冒泡 | sorted/合并 | sorted/冒泡 |
|---|---|---|---|---|---|---|
| 1000 | 0.0336 | 0.0015 | 0.0001 | 22× | **17×** | 386× |
| 2000 | 0.1470 | 0.0022 | 0.0001 | 65× | **16×** | 1027× |
| 4000 | 0.5887 | 0.0072 | 0.0004 | 81× | **16×** | 1309× |
| 8000 | 2.8712 | 0.0168 | 0.0013 | 171× | **13×** | 2250× |

**解读**：
- sorted() 是 Python 内置 Timsort（C 实现的 Timed-Powersort 变体），**比我的纯 Python 合并排序快 13~17 倍**——这就是"轮子 vs 自造"的典型差距：同样 O(n log n)，C 实现常数项远小于纯 Python。
- sorted() **比冒泡快 386~2250 倍**，而且 n 越大倍数越大——O(n²) 在 n=8000 时已完全不可用。
- 工程上**永远优先用内置 sorted()**，除非你要教学演示或面试手写。

## 六、独立研究任务（20 分）

### 6.1 减治法 vs 分治法——二分查找到底归谁？（8 分）

**一句话区分**
- **分治 Divide-and-Conquer**：拆成**多个子问题**，**每个都解**，最后**合并**所有子解。
- **减治 Decrease-and-Conquer**：拆成多个子问题，但**只解其中一个**（舍弃其余），**不需要合并**。

| 维度 | 分治 | 减治 |
|---|---|---|
| 子问题数量 | 多个，都要解 | 多个，只解一个 |
| 是否合并 | 需要 | 不需要 |
| 时间复杂度量级 | 通常 O(n log n) 或更高 | 通常 O(log n) 或 O(n) |
| 代表算法 | 合并排序、快速排序、Karatsuba 乘法 | 二分查找、欧几里得 gcd、随机选择 |

**关键判断点：有没有"舍弃"子问题 + 有没有"合并"子解。**

**二分查找归属：减治法。**

- 每次把规模折半后，**只在一边继续**（target 小就左、target 大就右），另一半直接**舍弃**——多个子问题只解一个。
- 找到就返回下标，没找到就继续——**完全不需要合并**步骤。

这和合并排序形成鲜明对比：合并排序两半都要排好，然后 merge 在一起——标准分治。二分查找是减治的教科书例子。

### 6.2 sys.setrecursionlimit + 10 万元素会不会撞递归上限？（7 分）

**Python 默认递归上限 = 1000**（`sys.getrecursionlimit()` 返回值）。

**合并排序 10 万元素的理论递归深度** = ceil(log₂100000) = **17**。

**实测**：
- 100000 个随机元素 → merge_sort 成功跑通 ✅，耗时正常，结果校验正确。
- 17 层深度 vs 1000 上限 → **远远碰不上**。

**人为把上限降低验证递归真的有上限**

| 人为设置的上限 | merge_sort 10 万元素 |
|---|---|
| 20 | ✅ 成功（20 > 理论深度 17）|
| 15 | ❌ RecursionError 炸了（15 < 17）|
| 10 | ❌ 炸了 |
| 5 | ❌ 炸了 |

**结论**：
- `sys.setrecursionlimit(N)` 控制 Python 递归深度上限，超过就抛 RecursionError。
- 默认 1000 对合并排序这种 O(log n) 深度的算法绰绰有余。
- 工程上几乎没人调这个——除非你在写深度神经网络反向传播（每层一个递归调用）或 AST 遍历，那种深度才可能真上千。
- 另外，**递归 ≠ 分治**——合并排序也可以写成纯迭代版本，递归只是 Python 实现分治最顺手的一种写法。

### 6.3 随机数组 vs 逆序数组——合并排序耗时几乎不变，为什么？（5 分）

**实测对比**

| n | 随机数组耗时 | 逆序数组耗时 | 比值 | 结论 |
|---|---|---|---|---|
| 1000 | 0.0019s | 0.0015s | 1.25 | 有微差 |
| 2000 | 0.0037s | 0.0020s | 1.84 | 有微差 |
| 4000 | 0.0069s | 0.0073s | **0.94** | **几乎不变** ✅ |
| 8000 | 0.0177s | 0.0158s | **1.12** | **几乎不变** ✅ |

**为什么几乎不变？**

合并排序的工作量可以拆成两步看：

**分解阶段**：无论输入是随机、升序、逆序，都是从中间**一刀切**。这一步和数据分布**完全无关**，成本恒定 O(log n) 层递归。

**合并阶段**：双指针扫描两个有序子表，每放一个元素就比较一次。无论 `left[i] ≤ right[j]` 还是反过来，**比较次数总量都恒等于 len(left) + len(right)**——因为每放一个元素要么 left 指针前进、要么 right 指针前进，不会有跳过。

所以从渐近意义上说，**合并排序不存在"最好情况"和"最坏情况"**——它对任何输入的复杂度都是严格 O(n log n)。这既是它的优点（最坏情况也不会炸，对比快排逆序会退化到 O(n²)），也是它不如快排快的原因（快排平均 O(n log n) 常数更小）。
